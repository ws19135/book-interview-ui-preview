## 這一版做了什麼

依 Owner 2026-09-06 的補充裁決，把**整案一個製作方**的模型改成**逐節目**，

視覺回到實機那一版：頂端四個入口的導覽列、細線分隔、少色塊。

| 項目 | 這一版 | 正式系統現況 |

| **製作方逐節目** | 每個答應的節目各自決定「公司統一發包」或「訪談節目自己處理」；公司做的再決定剪輯內部或外包 | 現行是每案一個製作方欄位 |

| **雙方確認名單** | 第 4 階段要「我方送出」＋「對方回覆確認」兩個都有才能往下；並列出對方想上但這次不安排的節目與原因 | 現行只有單向的確認連結 |
| **視覺** | 回到實機那一版：導覽列、細線、無色塊 | — |

## 引導動線（2026-09-06 加）

同事不用自己想先點哪個。入口頁把三個功能排成 ①②③，
下一個該走的會標「建議接下來走這個」，走完自動打勾。

```
入口頁 ①②③ ──► 前情提要 ──► 階段 1…N ──► ★ 小結頁 ──┐
   ▲                          （階段清單全程可見          │
   │                            走過的可以點回去）        │
   └───────────── 接著走下一條 ◄────────────────────────┘
                              三條都走完 ──► 最後四題
```

- **階段清單**：每一階段都看得到全部步驟，走過的打 ✓ 且可點回去，現在這一步紅底線。
- **小結頁**：每走完一條，先告訴你「剛剛完成了什麼」，再帶你接下一條。
- **需求一進來就帶著對方想上的節目**，第 2 階段的「審核」才有東西可審。

## 三個入口

```
入口頁
 ├─ 新書訪談邀約（8 階段）
 │   1 建立需求與指定承辦     →  2 審核想上的節目並補推薦
 │   3 處理費用或例外審核     →  4 雙方確認節目名單
 │   5 記錄節目邀約回覆       →  6 逐節目確認製作方與訪談時間
 │   7 逐節目追蹤錄音上架素材 →  8 完成案件並查看歷程
 │
 ├─ 新書預告登記（5 階段）
 │   1 登記新書 → 2 勾選想上的節目 → 3 已經有人在等
 │   4 書況有變 → 5 通知受影響的人
 │
 └─ 即將出版新書（1 頁）
     依上市月份排序 · 顯示希望的兩個檔期與在等的節目數 · 一鍵轉成訪談需求
```

## 逐節目的分流

```
這一集由誰做？
 ├─ 公司統一發包 ─┬─ 剪輯發公司內部做      → 自己剪 → 上架
 │                └─ 不勾（＝發外包）      → 建立外包交辦單
 │                                            待處理→已收到→處理中→已完成 → 上架
 └─ 訪談節目自己處理                        → 交給節目方上架
```

⭐ 外包交辦的資料結構**正式系統已經有了**（交辦對象／用途／期望完成日／狀態），
缺的是這個勾選與實際串接。邊界維持：只存不透明的外部編號，⛔ 不讀寫外包系統內部資料。

| 每一集都已上架或不予上架 | |

## ⏸ 先保留、這一版不顯示

**訪談時間與公司日曆預約系統串接**——Owner 表示後續可能會做，
這一版只在框架裡保留位置，⛔ 介面上不顯示。真的要做的時候，
